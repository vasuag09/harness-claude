# Spec: Bug-fix fast lane (`/fix`)

Status: complete (v0.12.0) · verified

## Problem

The harness pipeline is **greenfield-shaped** — `/spec → … → /ship` assumes you're *building a
new feature*. When something is **already broken** ("prod throws on empty input", "this test went
red", "users report X"), there's no entry point: over-ceremonying it through `/spec` is wrong
(there's no feature to spec), and skipping the harness loses the TDD + review + security gates.

`/fix` gives bugs their own disciplined entry. It does the **bug-specific** part — reproduce →
root-cause → failing regression test → minimal fix-plan — then hands off to the **existing**
pipeline (`/implement` → `/verify` → `/ship`) so the fix rides the proven gates. The
non-negotiable discipline: **reproduce as a failing test FIRST** (capture the bug RED before
fixing), and keep the fix **minimal** (scoped to the cause — no refactor-while-you're-in-there).

## In scope

- A new opt-in **`/fix` skill** (entry point): from a bug report to a merge-ready fix-plan with a
  failing regression test, then a clean hand-off to the existing pipeline.
- **Reuse, don't rebuild:** delegates to `harness-claude:tdd-guide` (the regression test),
  and the fix then flows through `/implement` → `/review` + `/security-review` → `/verify` → `/ship`.
- Wiring into `rules/workflow.md` (bug-fix entry) + docs.

## Out of scope

- A new debugger/runtime, profiler, or any new dependency/MCP server.
- A new agent — the skill is the lead; it reuses `tdd-guide`, `code-reviewer`,
  `security-reviewer`, `build-error-resolver`.
- A self-contained lane that re-implements verify/ship — `/fix` is a *parallel entry*, not a
  rewrite of the pipeline.
- Auto-committing — git boundary holds.

## Acceptance criteria

- [x] **AC-1 (reproduce-first):** given a bug report, `/fix` produces a **reproduction** — a
      failing test (RED) that captures the bug — *before* any fix is written. If a reliable
      automated repro isn't possible, it states why and records concrete manual repro steps.
- [x] **AC-2 (root cause):** it identifies and states the **root cause**, not just the symptom
      (the actual defect + why it produces the reported behavior).
- [x] **AC-3 (minimal fix-plan):** it produces a fix-plan scoped to the cause — explicitly no
      unrelated refactors; the smallest change that makes the RED test GREEN.
- [x] **AC-4 (regression test via tdd-guide):** the reproduction is added as a durable regression
      test through `harness-claude:tdd-guide` (RED → GREEN), so the bug can't silently return.
- [x] **AC-5 (hand-off, not rebuild):** `/fix` hands the fix-plan + RED test to `/implement`, then
      the change rides the existing `/review` + `/security-review` + `/verify` + `/ship` gates —
      `/fix` does not duplicate those gates.
- [x] **AC-6 (opt-in + git boundary):** `/fix` is invoked explicitly (off by default), and it
      never commits/pushes/branches.
- [x] **AC-7 (no new agent / dep / MCP):** the skill is the lead and reuses existing agents; no
      new dependency, no new MCP server, no new runtime.
- [x] **AC-8 (wiring/docs synced):** `rules/workflow.md` (bug-fix entry), README, CLAUDE.md,
      docs/SKILLS.md, manifests (version + skill count 29→30), and ROADMAP are reconciled.

## Constraints

- Lean, reuse-first, immutable patterns; files < 800 lines.
- Must compose with the existing Verify/Ship gates rather than duplicating them.
- House-style consistent with `skills/operate/SKILL.md` and `skills/orchestrate/SKILL.md`.

## Reuse decision (from /research)

Markdown-only skill, so reuse is entirely in-repo — no library/registry research applies.

- **Build new (novel part only):** `skills/fix/SKILL.md` — the bug-specific lead (reproduce →
  root-cause → failing regression test → minimal fix-plan). No existing skill covers this.
- **`/build-fix` does NOT overlap:** it's scoped to *build/type/compile errors* (get the build
  green, minimal diff via `build-error-resolver`). `/fix` is for *behavioral/logic bugs* with
  reproduce-as-failing-test-first discipline. Complementary — `/fix` may *call* `/build-fix` to
  keep the build green mid-fix. The skill must state this boundary so the two don't blur.
- **Hand-off seam is correct:** `/implement` already opens each phase with "failing test against
  an acceptance criterion (RED) → minimum code (GREEN)" via `tdd-guide`. `/fix` hands it a
  fix-plan + already-RED regression test — fits that contract with no new machinery. `/verify` →
  `/ship` follow unchanged. `/fix` must NOT re-implement verify/ship.
- **Agents reused:** `tdd-guide` (regression test), `code-reviewer` + `security-reviewer` (gates),
  `build-error-resolver` (build green). No new agent / dep / MCP / runtime (AC-7 ✓).
- **House style:** matches `/operate` + `/orchestrate` — opt-in markdown discipline layer, off by
  default, git boundary holds.
- **Risk:** none from dependencies (zero new); only risk is conceptual overlap with `/build-fix`,
  mitigated by stating the behavioral-vs-build boundary in the skill.
