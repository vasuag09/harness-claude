# v0.10.0 — Long-running agents (Phase 4)

Status: **verified — ready to ship** (review + security-review + test + verify all passed) · Version: 0.10.0 · Type: numbered roadmap phase (Phase 4)

## Problem
The harness can drive one bounded task well, but has no disciplined way to let an agent
**run unattended for a long time** — an autonomous loop or a scheduled wake-up — without
risking silent drift: spinning on the same fix, burning budget forever, or slowly breaking
the code while believing it's helping. Phase 4 closes that gap: *let it run long, and make
sure it can't silently diverge from the spec.*

## Decision (build-scope ADR)
**Thin discipline layer over the platform's existing `/loop` and `/schedule`** — not a new
runtime. The platform already provides the loop/schedule engine; the harness adds the
operator judgment and safety it lacks: a **loop-operator agent**, **guardrails that halt**,
**durable checkpoint state**, and **drift self-checking wired to the Phase-2 eval skills**.
- Rejected: a self-contained loop/scheduler runtime (duplicates working platform primitives;
  violates the harness's reuse-first creed and lean-base principle).
- Rejected: agent + rules only (nothing *enforces* the guardrails; the "can't drift"
  guarantee would rest on the agent following prose).

## In scope
- **`/operate` skill** (or equivalent driver) — starts/supervises a long-running task on top
  of `/loop` (interval) or `/schedule` (cron), enforcing the guardrails and checkpoint cadence.
- **`loop-operator` agent** — knows how to run a task across iterations safely: decide next
  action, run a checkpoint, decide continue/halt, write durable state.
- **Guardrails (mandatory, each can HALT the run):**
  - **Iteration cap** — hard ceiling on iterations.
  - **Budget cap** — wall-clock and/or token/cost ceiling.
  - **Drift halt** — N consecutive failing checkpoints → stop and surface.
  - *(recommended-optional)* No-progress halt — no measurable change across K iterations → stop.
- **Durable checkpoint state** — a single file per run recording: objective, iteration count,
  budget spent, last checkpoint verdict, consecutive-fail count, last action, and halt reason.
  Survives restarts / resume.
- **Drift self-check** — at each checkpoint the operator runs **`/health`** (test/lint pulse) and
  **`/eval`** (acceptance-criteria gate) against the run's spec; the defined failure pattern trips
  the drift halt. Reuses Phase-2 skills directly; no new detector.
- **Wiring & docs** — ROADMAP Phase 4 → ✅; rules note on long-running discipline; manifests
  (plugin.json + marketplace.json) version + counts; README/CLAUDE.md/SKILLS.md skill list.

## Out of scope
- A self-contained loop executor or scheduler (use the platform's). · Multi-agent fan-out
  (that's Phase 5). · Computer-use (Phase 6). · A brand-new drift-detection algorithm.

## Reuse decision (from /research — wrap, don't build)
Thin-discipline-layer confirmed viable; every heavy piece already exists.
- **Engine — adopt as-is:** platform `/loop` + `ScheduleWakeup` (iteration driver; delay clamped
  [60,3600]s, same-session, fresh context per firing) and `/schedule` + `CronCreate` (cron runs).
  The `Workflow` tool (multi-agent fan-out) is Phase 5 — not used here.
- **Drift check — reuse directly (AC-4):** `/health` = `node scripts/eval/continuous.js`
  (exit 0/1/2, secret-safe, `.claude/eval/continuous/latest.json`); `/eval` =
  `node scripts/eval/checkpoint.js [spec.md]` (exit 0/1/2). Operator shells them, reads exit
  codes — no new detector.
- **Durable state — port the helper, not the format:** reuse `_lib.js stateDir(cwd, sub)` (resolves
  `.claude/<sub>`, abs-path traversal guard) to write **`.claude/runs/<id>.json`**; mirror the
  uniform exit-code contract + capture-nothing secret rule. Resolves the open question: dedicated
  `.claude/runs/` JSON, **not** a prose session file.
- **Build new (small):** (1) a run-state + guardrail Node module (iteration cap / budget /
  consecutive-fail; mirrors `continuous.js`); (2) `/operate` skill + `loop-operator` agent (markdown
  orchestration). No new dep, no new MCP server (AC-8 holds by construction).

## Constraints (added from /research)
- **State file is the source of truth across firings** — each `/loop` firing may be a fresh context;
  iteration count, budget spent, and consecutive-fail must persist in `.claude/runs/<id>.json` and be
  restored each firing (this *is* AC-5).
- **Budget guardrail leans on wall-clock + iteration count** in v1 — a plain `/loop` does not expose
  token/cost cleanly (only `Workflow` does); treat token/cost as best-effort/approximate.

## Acceptance criteria
*(All verified — unit: `scripts/operate/test-operate.sh` 35/35; live: scratchpad real `make test`
run, scenarios A–E.)*
- [x] **AC-1 Halts on iteration cap.** Given a run with `maxIterations = N`, when N iterations
  complete, then the run stops and the checkpoint file records `haltReason: iteration-cap`.
  *(Live A: 3 passing iterations → `halt=iteration-cap`, exit 1.)*
- [x] **AC-2 Halts on budget.** Given a wall-clock or token budget, when it is exceeded at a
  checkpoint boundary, then the run stops with `haltReason: budget`.
  *(Live D: real elapsed 41ms > `--budget-ms 1` → `halt=budget`.)*
- [x] **AC-3 Halts on drift.** Given a run whose checkpoint (`/health` or `/eval`) fails N
  consecutive times, then the run stops with `haltReason: drift` and surfaces the failing
  criterion — it does **not** continue silently. The failing criterion is surfaced on the
  checkpoint's streamed output *and* persisted secret-safely in the eval artifact
  `.claude/eval/continuous/latest.json` (name/command/pass), so a headless caller can recover it
  after the fact. *(Live B: 2 real `make test` failures → `halt=drift`; surfaced "FAIL: acceptance
  check 'auth flow' regressed" + `re-run: make test`.)*
- [x] **AC-4 Checkpoint cadence reuses Phase-2 skills.** At each checkpoint the operator invokes
  `/health` and (when a spec exists) `/eval`; no new drift-detection code duplicates them.
  *(Live A: auto-detected `make test` via continuous.js; Live E: `/eval` ran checkpoint.js on a
  real spec and surfaced "AC-1 FAIL login works".)*
- [x] **AC-5 Durable state survives interruption.** Given a run interrupted mid-flight, when it
  resumes, then iteration count, budget spent, and consecutive-fail count are restored from the
  checkpoint file (not reset to zero). *(Live C: firing 1 → iteration 1 / 45ms; fresh-process
  resume → iteration 2 / 152ms, `startedAtMs` preserved — accumulated, not reset.)*
- [x] **AC-6 Clean halt always reports.** On any halt (success, cap, budget, drift), the operator
  emits a final summary: iterations run, budget spent, last verdict, halt reason. *(Every live
  scenario printed `run <id>: N iteration(s), Mms spent, last verdict V, halt=R`.)*
- [x] **AC-7 Opt-in, base stays lean.** The capability is a module that is **not** wired into the
  default pipeline or any always-on hook; running long is always explicit. *(Test asserts no hook
  references the module; skill frontmatter + body state opt-in.)*
- [x] **AC-8 No new MCP servers / heavy deps.** Delivered as skill + agent + state-file wiring;
  `.mcp.json` server count unchanged. *(Modules require only `_lib.js` + node builtins; no dep
  added.)*
- [x] **AC-9 Reference integrity passes.** `scripts/check-reference-integrity.sh` green with the
  new skill/agent registered; full local `test-*.sh` suite green. *(16/16 suite green; integrity ✓.)*

## Constraints
- **Reuse-first / lean base** — no runtime rebuild; ride platform `/loop` + `/schedule`.
- **Safety > autonomy** — guardrails must *halt*, not merely warn; the accuracy floor
  (don't trade correctness for a longer run) is non-negotiable.
- **Git boundary** — a long run must never commit/push/branch unless the user explicitly armed it.
- **Token discipline** — checkpoints are cheap by default (`/health` pulse); `/eval` runs when a
  spec is present.
- **Prove-before-promote** — validate on a real long task in isolation before any default wiring.

## Open questions (with recommended defaults)
- **Trigger surface:** one `/operate` skill wrapping both interval and cron, vs. two thin skills?
  → *Default: one `/operate` with an interval-or-schedule arg; smaller surface, single operator.*
- **Drift threshold N:** consecutive-fail count before halt. → *Default: N = 2 (one failure may be
  transient; two is a trend). Configurable per run.*
- **Where state lives:** reuse `.claude/sessions/` dated files vs. a dedicated `.claude/runs/`.
  → *Default: a dedicated `.claude/runs/<id>.json` — session files are prose snapshots; run state is
  structured and machine-read each iteration. Resolve in `/research` + `/architect`.*
