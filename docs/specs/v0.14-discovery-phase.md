# Spec: `/discover` — the discovery phase (vague intent → chosen direction)

**Status:** complete (v0.14.0) · verified · **Type:** new pre-PLAN skill (markdown lead, opt-in/conditional)

## Problem

The pipeline's front door is `/spec`, which presupposes the user can already state *what*
they want. Every entry point assumes a request exists: `/spec` sharpens a known request,
`/research` is reuse-first on a known problem, `/design` does UX for an already-chosen
feature. **Nothing serves the altitude above `/spec`:** a user with a vague itch ("make this
better", "what could I build with X") who doesn't know the *shape* of the answer or what's
even possible. `/discover` fills that gap — a divergent→convergent move that turns vague
intent into a framed problem + one chosen direction that `/spec` can consume.

This workflow already recurs informally (it's what the assistant does whenever a user opens
vague); `/discover` makes it a repeatable, *disciplined* step rather than an ad-hoc improvisation.

## In scope / Out of scope

**In:**
- A new `skills/discover/SKILL.md` markdown-lead skill (no new agent/dep/MCP/runtime).
- A structured four-beat flow: interrogate → map opportunity space → converge → hand off.
- The convergence discipline (the heart of this spec — see acceptance criteria).
- A clean handoff seam to `/spec` (produces an *intent statement* + chosen direction).
- Conditional firing: detects when a request is already spec-ready and routes straight to
  `/spec` without ceremony.
- Pipeline docs wiring (CLAUDE.md, ROADMAP.md, workflow.md, README, SKILLS.md, manifest counts).

**Out:**
- Writing acceptance criteria — that stays `/spec`'s job (the seam must stay clean).
- Heavy reuse-first searching — that stays `/research`'s job; `/discover` does only light
  feasibility grounding to keep candidate directions honest.
- Building anything / feasibility prototyping — that's a future `/spike`, not this.
- Auto-firing on every request, or forcing the interview on already-clear requests.
- A new orchestrator command; wiring into `/harness-plan` is deferred (noted seam).

## Acceptance criteria

**Convergence discipline (locked):**
- [x] **AC-1 Bounded divergence.** Given any vague intent, when `/discover` maps the
      opportunity space, then it presents **≤5** candidate directions — never an unbounded dump.
- [x] **AC-2 Forced convergence.** `/discover` **cannot exit to `/spec`** without naming exactly
      **one** recommended direction (an optional runner-up shortlist is allowed, but the
      recommendation is singular and explicit). An unranked list is not a valid exit state.
- [x] **AC-3 Decision, not brainstorm.** The terminal output is a *decision* (chosen direction +
      one-line rationale), not a catalog of ideas. A run that ends in "here are some options"
      with no recommendation fails.
- [x] **AC-4 Conditional firing (anti-ceremony).** Given an *already spec-ready* request, when
      `/discover` self-assesses it, then it says so and routes straight to `/spec` **without**
      running the interrogation interview. The discovery flow only runs on genuine vagueness.
      *Operationalized (testable):* the self-assessment uses a **critical-unknowns gate** — if fewer
      than 3 of the five critical unknowns (goal, target user/surface, scope boundary, success signal,
      hard constraints) are missing (i.e. ≤2 absent), the request is spec-ready and is routed onward.
- [x] **AC-5 Socratic intake.** `/discover` asks focused clarifying questions (via
      `AskUserQuestion`) to surface the real goal/pain/constraint **before** proposing directions;
      it does not invent and pursue a direction unilaterally.

**Handoff & grounding:**
- [x] **AC-6 Clean seam to `/spec`.** The handoff is an **intent statement** (framed problem +
      chosen direction + key constraints), explicitly **not** acceptance criteria. Given a
      completed `/discover`, when handed to `/spec`, then `/spec` has a clear-enough request to
      restate without re-interrogating from scratch.
- [x] **AC-7 Grounded options.** Candidate directions are grounded in feasibility/codebase fit
      (light touch — leaning on existing context/`mgrep`), not pure speculation; the heavy
      reuse-search is explicitly deferred to `/research`.
- [x] **AC-8 Lean output.** The discovery brief fits one screen (problem framing + ≤5 options +
      the one recommendation + handoff statement).

**Housekeeping:**
- [x] **AC-9 Docs reconciled.** Skill count, pipeline diagrams, ROADMAP, workflow.md, README,
      SKILLS.md, and `.claude-plugin` manifests all updated to include `/discover`; the
      reference-integrity guard passes.

## Reuse decision (from /research)

**Build new + port patterns** (no external dependency — markdown-lead skill, no library/registry surface):
- **Port from `prompt-optimizer`**: intent-detection + missing-context scan + "ask ≤3 clarifying
  questions if 3+ criticals missing, else state it" gate → realizes AC-5 (Socratic intake) and AC-4
  (spec-ready self-assessment / anti-ceremony discriminator).
- **Port from `shape`**: the interview → written-brief shape → realizes AC-6 (intent-statement handoff).
- **Build new (the genuine delta — nothing does it):** the divergent→convergent core — bounded
  opportunity generation (≤5, AC-1) + forced convergence to one recommendation (AC-2/AC-3). Every
  analog (`prompt-optimizer`, `shape`, `blueprint`, `ccg:enhance`) presupposes the *what* and refines
  the *how*; none diverge across *what to build* then force a single pick. Confirms the redundancy test.
- **Risk:** zero dependency risk — porting *patterns*, not code, from same-ecosystem skills.

## Constraints

- **House style:** markdown-lead skill, opt-in/conditional, no new agent/dependency/MCP/runtime
  (consistent with `/fix`, `/observe`, the design gate).
- **Anti-bloat:** must not duplicate `/spec`, `/research`, or `/design` — strictly upstream of all
  three (the redundancy test in the spec body must hold).
- **Lean/lazy ethos:** bounded divergence + forced convergence; never an open-ended brainstorm.
- **Git boundary holds:** `/discover` never commits/pushes/branches.

## Open questions (with recommended defaults)

1. **Conditional vs. always-on entry?** → *Default:* conditional, like the design gate — fires
   only on vague intent, self-detects spec-ready requests and steps aside (AC-4). Clear requests
   still start at `/spec`.
2. **Wire into `/harness-plan` as a pre-step now, or ship standalone first?** → *Default:* ship
   standalone `/discover` first; note `/harness-plan` pre-step as a follow-up seam (mirrors how
   `/orchestrate` shipped standalone before `/implement` wiring). Avoids scope creep.
3. **Persist the discovery brief to a file?** → *Default:* no — conversation output only (lean);
   multi-session work can capture it via `/save-session`. Add a file only if a need appears.
