# Spec: Phase 5 — Multi-agent orchestration (`/orchestrate`)

Status: complete (v0.11.0) · Target: v0.11.0

## Problem

Non-trivial work that spans many independent files/modules is currently driven serially by
the main agent. There is no codified, invokable way to **decompose a task, fan out to
multiple workers in parallel, guarantee one-writer-per-file, and reconcile results** — with
explicit per-worker contracts (input, tool scope, ownership boundary, output shape).

The platform already provides the *mechanics* (the Workflow tool: deterministic parallel /
pipeline fan-out). The harness's contribution is the **discipline layer**: how to split work
safely, who owns which files, and how each worker is briefed and reconciled. This mirrors how
Phase 4 wrapped `/loop`+`/schedule` rather than building a new runtime.

## In scope

- An **`/orchestrate` skill** (the lead/boss): turns a task into a written decomposition
  (by file / module / pipeline stage), assigns disjoint file-ownership, fans out via the
  platform **Workflow tool**, reconciles worker summaries into one result.
- A **worker agent-contract template** (reference doc): one clear input, scoped read/write
  tool set, an ownership boundary (the only files it may write), one structured-summary output.
- **File-ownership discipline = assignment-by-plan**: the lead assigns disjoint write-sets;
  workers are read-only on files they don't own. The one-writer-per-file invariant holds by
  construction, verified before fan-out.
- Wiring into `rules/workflow.md` + docs; opt-in, off by default.

## Out of scope

- New MCP servers or new runtime dependencies (reuse the Workflow tool + existing subagents).
- New executable coordination scripts / lock-ledger runtime (assignment-by-plan needs none).
- Git worktree isolation as the locking mechanism (we lock by plan, not by isolation).
- Replacing `rules/agents.md` — this *operationalizes* its two modes into an invokable skill.
- Computer-use / browser agents (Phase 6).

## Acceptance criteria

- [x] **AC-1 (decomposition):** `/orchestrate <task>` produces a written plan listing
      subtasks, each subtask's owned files, its read/write tool scope, and the
      dependency/parallel structure (what runs concurrently vs sequenced).
- [x] **AC-2 (one-writer-per-file):** the plan's write-sets are pairwise disjoint across any
      set of concurrently-running workers; the skill verifies and refuses to fan out if two
      concurrent workers would write the same file, naming the conflict.
- [x] **AC-3 (parallel where independent):** subtasks with disjoint ownership and no
      dependency run in parallel via the Workflow tool; dependent subtasks are sequenced.
- [x] **AC-4 (explicit contracts):** each worker is dispatched with one clear input, a scoped
      tool set (read-only unless it owns the file), its ownership boundary, and is required to
      return a structured summary (not a raw dump).
- [x] **AC-5 (reconciliation):** the lead collects worker summaries into one result and
      surfaces any conflicts / failed workers rather than silently dropping them.
- [x] **AC-6 (engine = Workflow tool):** fan-out runs on the platform Workflow tool; no new
      runtime, no new dependency, no new MCP server is added.
- [x] **AC-7 (opt-in + git boundary):** the skill is off by default (invoked explicitly), and
      a run never commits/pushes/branches unless the user explicitly arms it.
- [x] **AC-8 (wiring/docs synced):** `rules/workflow.md`, README, CLAUDE.md, docs/SKILLS.md,
      manifests (version + skill/agent counts), and ROADMAP (Phase 5 ✅) are reconciled.

## Constraints

- Lean: skill + reference docs only; files < 800 lines; immutable patterns; reuse-first.
- Must compose with the existing `/harness` phases and the 8 scoped subagents.
- Token discipline: workers return summaries, not raw dumps (per `rules/agents.md`).

## Open questions (resolved)

- **Deliverable shape** → skill + worker-contract template only (no scripts/runtime). *(resolved)*
- **File locking** → assignment-by-plan (disjoint write-sets), not worktrees or a lock ledger. *(resolved)*
- **Engine** → platform Workflow tool drives the fan-out. *(resolved)*

## Reuse decision (from /research)

- **Wrap (don't build): the first-party Workflow tool** as the fan-out engine. It already
  provides `parallel()`/`pipeline()` (→ AC-3), `agent(prompt, {schema})` with tool-layer
  validated structured output (→ AC-4/AC-5), is first-party (→ AC-6 no new dep/MCP), and is
  gated behind explicit opt-in (→ AC-7 — invoking `/orchestrate` *is* the opt-in). No external
  library and no GitHub adoption applies — it is a platform primitive, not an import.
- **Build new (the genuinely novel part): the discipline layer only** — task decomposition,
  disjoint-write-set assignment + the one-writer-per-file check (AC-1/AC-2), worker contracts,
  and reconciliation. Nothing in-repo does this; the existing `/harness*` orchestrators only
  *sequence* phase skills, they don't decompose arbitrary multi-file work with ownership.
- **Operationalize, don't duplicate `rules/agents.md`:** it defines two modes (sequential +
  iterative-retrieval ≤3 cycles) but **no parallel fan-out mode**. `/orchestrate` is that third
  mode, and must honor the file's standing rules — cheapest-sufficient model, summaries-not-
  dumps, minimum-tool-set scoping, read-only unless owner.

### Key API facts the plan must respect

- Native collision answer is `isolation:'worktree'`; we use **assignment-by-plan** instead, so
  disjoint owners write the shared tree directly. `isolation:'worktree'` is the documented
  escape hatch only when disjointness cannot be guaranteed.
- Workflow runs **in background**, returns a task ID, notifies on completion → treat fan-out as async.
- Concurrency caps at ~`min(16, cores−2)`; excess queues → scale fan-out to task size.
- `args` must be real JSON (not a stringified blob); every script needs the pure-literal
  `export const meta = {…}` header.

### Risks of the chosen engine

- Spawns many agents / high token use → the skill must size fan-out to the task, not fan out
  blindly (mitigated by AC-1 decomposition + summaries-not-dumps).
- Background/async completion model → the skill must handle reconciliation after notification,
  not assume synchronous returns.
- Opt-in gating means `/orchestrate` is correctly off by default (consistent with AC-7).
