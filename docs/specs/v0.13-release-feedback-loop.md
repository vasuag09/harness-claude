# Spec: Release & feedback loop (`/deploy` + `/observe`)

Status: complete (v0.13.0) · verified

## Problem

The harness pipeline is **one-way and stops at the repo boundary**. `/spec → … → /ship`
prepares a clean commit/PR and halts. Nothing happens *after* the change leaves the repo:
there's no disciplined way to push it to a running environment, and no way for **production
reality** (an error, a log line, a metric alert) to flow *back* into the harness. The pipeline
is a line, not a loop.

This phase closes the loop with two opt-in skills that bracket the live environment:

- **`/deploy` (#1)** — after `/ship`, drive the change out to a running environment using the
  **project's own deploy mechanism**, smoke-test the *deployed* artifact, and keep a guarded
  rollback path. Deploy is more outward-facing than `git push`, so it extends the harness's
  boundary discipline: **plan + check, then HALT and require an explicit arm** before any real
  outward action ("arm-to-fire").
- **`/observe` (#2)** — take a production signal the user **brings to it** (a pasted stack trace,
  log snippet, error text, or an issue/monitoring URL), triage it into a located, reproducible
  failure, and route it into the existing **`/fix`** lane. No polling, no credentials, no new MCP.

Together: `/ship → /deploy → (prod) → /observe → /fix → …` — the line becomes a loop.

## In scope

- A new opt-in **`/deploy` skill**: detect the project's existing deploy mechanism → plan +
  identify rollback path → pre-deploy smoke checks → **arm-to-fire HALT** → on arm, execute the
  project's own deploy command (in tmux) → smoke-test the deployed artifact → guarded rollback on
  failure.
- A new opt-in **`/observe` skill**: parse a brought signal → locate the failing area in code
  (mgrep/graph) → shape a repro seed → hand off to `/fix` with root-cause-area context.
- Wiring that makes the **closed loop explicit** in `rules/workflow.md` + docs.

## Out of scope

- **Prescribing or installing a deploy stack.** `/deploy` orchestrates whatever the project
  already has (Vercel CLI, Dockerfile, Makefile target, CI config, `package.json` scripts); it
  ships no Vercel/Docker/k8s adapter and adds no dependency.
- **Active monitoring / polling.** `/observe` is **bring-a-signal** only. Polling Sentry/Datadog/
  CloudWatch (MCP + credentials + a running poller) is explicitly deferred — a noted seam, built
  only if/when a backend exists (YAGNI).
- **Auto-deploy without a human arm.** The arm-to-fire HALT is non-negotiable.
- A new agent, runtime, MCP server, or dependency — both skills are *leads* that reuse existing
  agents (`build-error-resolver`, and `/fix`'s chain) and existing tools (tmux, `/health`, mgrep).
- Re-implementing `/fix` — `/observe` routes *into* it; it does not duplicate reproduce/root-cause.

## Acceptance criteria

### `/deploy` (#1)

- [x] **AC-D1 (detect, don't prescribe):** `/deploy` detects the project's *existing* deploy
      mechanism (e.g. `vercel.json`/`Dockerfile`/`Makefile`/CI config/`package.json` scripts) and
      uses it. It installs/prescribes no stack and adds no dependency. If none is detected, it says
      so and stops (does not invent one).
- [x] **AC-D2 (rollback path identified up front):** before deploying, it names the concrete
      rollback path for the detected mechanism (e.g. `vercel rollback`, redeploy previous image
      tag / previous SHA) and surfaces it in the plan.
- [x] **AC-D3 (smoke-test the deployed artifact):** after a deploy, it runs a smoke check against
      the **deployed** artifact (health endpoint / smoke suite / reusing `/health` against the
      deployed target) — not just local tests.
- [x] **AC-D4 (arm-to-fire boundary):** `/deploy` plans + runs pre-deploy checks, then **HALTS**
      and requires an explicit arm before executing any real outward deploy or rollback. Opt-in,
      off by default.
- [x] **AC-D5 (guarded rollback on failure):** if the post-deploy smoke fails, it surfaces the
      rollback command and, **only if armed**, executes it; otherwise it halts with the rollback
      ready. It never leaves a known-broken deploy silently in place.
- [x] **AC-D6 (long-running in tmux):** the (potentially long) deploy command runs in tmux per the
      harness tooling default, so it survives and streams.

### `/observe` (#2)

- [x] **AC-O1 (bring-a-signal intake):** `/observe` accepts a signal the user brings — pasted
      stack trace, log snippet, error text, or an issue/monitoring URL — and parses it into a
      structured failure description. No polling, no credentials, no new MCP.
- [x] **AC-O2 (locate the area):** it locates the likely failing component/area in the codebase
      (via mgrep / the graph), grounding the signal in real code rather than guessing.
- [x] **AC-O3 (repro seed + route to `/fix`):** it shapes a candidate reproducible failing case
      (or records concrete manual repro steps when automation isn't possible) and hands off to
      `/fix` with the root-cause-area context. It does **not** re-implement `/fix`'s
      reproduce/root-cause/minimal-fix discipline.
- [x] **AC-O4 (read-only + git boundary):** `/observe` is read-only until it routes to `/fix`; it
      never commits/pushes/branches.

### Shared

- [x] **AC-S1 (no new agent / dep / MCP / runtime):** both skills are leads reusing existing
      agents and tools; nothing new is installed.
- [x] **AC-S2 (loop closes, wiring/docs synced):** `rules/workflow.md` gains a "Release & feedback

## Reuse decision (from /research)

Markdown-only skills, so reuse is overwhelmingly in-repo. Confirmed seams (read, not assumed):

- **`/observe` → `/fix` hand-off is exact.** `/fix` step 1 is "reproduce first — capture the bug
  RED," and it explicitly accepts *manual repro steps* when automation isn't possible. So
  `/observe` hands `/fix` a **located failure + repro seed + root-cause-area context** — it must
  **not** produce the finished failing test (that's `/fix`'s job). AC-O3 reflects this.
- **`/deploy` smoke-test reuses `/health` verbatim.** `node scripts/eval/continuous.js --cmd
  '<shell>'` *replaces* the detected check set, so the deployed-artifact smoke (AC-D3) is
  `--cmd 'curl -fsS https://<deployed>/health'` (or the project's smoke suite) — secret-safe,
  zero new machinery. No new runner.
- **`arm-to-fire` borrows an existing concept.** `/operate` already says a run "never commits/
  pushes/branches unless you explicitly **arm** it." `/deploy` extends that same discipline to the
  outward deploy/rollback action (AC-D4/AC-D5). No durable run-state needed — `/deploy` is a single
  guarded action, not a loop, so it does *not* need `/operate`'s `.claude/runs/<id>.json` machinery.
- **Stack detection, not stack prescription.** `/deploy` detects the project's mechanism and uses
  it — including **delegating to existing platform skills when present** (e.g. `vercel:deploy` /
  `vercel:vercel-cli` are available this session) rather than reinventing. Adds nothing.
- **Long-running deploy → tmux** (existing tooling default); **build breakage mid-deploy →
  `build-error-resolver`** (existing agent). No new agent, dep, MCP, or runtime (AC-S1 ✓).
- **House style:** matches `/operate` + `/orchestrate` + `/fix` — opt-in markdown discipline layer,
  off by default, boundaries hold.
- **Risk:** zero from dependencies. Residual risk is the outward action itself — mitigated entirely
  by the arm-to-fire HALT + guarded rollback.
