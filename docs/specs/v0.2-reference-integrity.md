# v0.2 — Reference Integrity & Host Isolation

**Status:** spec (Plan phase) · **Owner:** Vasu · **Date:** 2026-06-16
**Precedes:** Phase 2 (eval loops). Evals are meaningless if the pipeline invokes the
wrong agents — this workstream makes the harness's own wiring deterministic first.

---

## 1. Problem

harness-claude is distributed as a plugin but its skills/agents reference each other by
**bare, un-namespaced names**, and assume companion tools (`mgrep`, `context7`, a code
graph) are present. Claude Code loads all plugins + personal config into **one flat
per-session namespace** — plugins are a packaging boundary, not a runtime sandbox. So on
any host that also has conventionally-named agents, the harness silently invokes the
wrong ones, and on any host without the companions, its instructions become dead text.

### Verified evidence (this machine, 2026-06-16)

- **All 7 harness agents collide on their bare name.** Each of `planner`, `architect`,
  `code-reviewer`, `security-reviewer`, `tdd-guide`, `build-error-resolver`,
  `refactor-cleaner` has ≥3 live definitions: the user's personal `~/.claude/agents/<n>.md`,
  the `everything-claude-code` plugin, and harness-claude. `code-reviewer` also collides
  with official `feature-dev` and `pr-review-toolkit` plugins.
- **Bare token resolves to the wrong agent.** `skills/plan/SKILL.md:11` says "delegate to
  the `planner` agent." `Agent(subagent_type:"planner")` resolves the unnamespaced
  definition first → `~/.claude/agents/planner.md` (a Chinese WBS decomposer, tools
  `Read,Write` only) — **not** harness-claude's SDLC planner. Silent degradation.
- **14 bare agent-invocation sites** in skill bodies + **8 bare refs** in skill
  descriptions. **0** use the namespaced form.
- **Orchestrators chain sub-skills by bare slash name** (`/plan`, `/review`, `/verify`,
  `/security-review`) — all of which have unnamespaced twins in a typical install.
- **Companion refs are unguarded in skills.** `mgrep`/`context7`/graph appear in 6 skills;
  the two *agents* that reference them already fall back to Grep, but the **skills do not**
  (`research/SKILL.md` asserts "use context7"/"use mgrep" with no fallback).

### Impact

Personal use is forgiving (the host happens not to misfire often). **Public-grade is
fragile:** the harness misfires on exactly the serious-user setups that have
`everything-claude-code` (the plugin it was modeled on), the official feature-dev /
pr-review plugins, or personal agents with standard names.

---

## 2. Goal & non-goals

**Goal:** every internal reference resolves **deterministically to harness-claude's own
component**, regardless of what else is installed; every companion-tool reference
**degrades gracefully** with a visible note when the companion is absent; a check
prevents regressions.

**Non-goals:** no new pipeline capabilities (no Phase 2–6 work); no behavior change to
what the agents/skills *do*; no change to the git boundary or hooks' core function.

---

## 3. Acceptance criteria

1. **AC-1 — Deterministic agent resolution.** Every agent invocation in every skill body
   and description uses the collision-proof form decided in §6. A fresh install on a host
   with conflicting `planner`/`architect`/`code-reviewer`/etc. invokes the harness's agent,
   verified by a run-trace showing the correct component fired.
2. **AC-2 — Deterministic skill chaining.** Every orchestrator → sub-skill reference uses
   the namespaced form, so `/harness-*` never routes into a foreign `plan`/`review`/`verify`.
3. **AC-3 — Guarded companion refs.** Every `mgrep`/`context7`/graph reference in a skill
   states the fallback inline (e.g. "use mgrep, or Grep/Glob if unavailable"), matching the
   pattern the agents already use. No skill asserts a companion as mandatory.
4. **AC-4 — Declared dependency contract.** The plugin documents what is **bundled**
   (its 7 agents, 3 MCPs) vs. **optional companion** (`mgrep`, `context7`, graph). A
   stranger can tell, before running, what is required vs. enhancing.
5. **AC-5 — Regression guard.** A check (script + CI) greps for bare internal
   agent/skill references and **fails** if any reappear. Keys off the plugin name from the
   manifest, so a fork/rename auto-updates the expectation.
6. **AC-6 — Self-contained smoke test.** Documented procedure proving a `/harness-plan`
   run on a host with name-colliding agents delegates to the harness's own planner.

---

## 4. Reuse decision

No external library applies — this is config/prose hygiene over our own files. Reuse is
**internal**: the fallback-guard wording the two agents already use
(`agents/planner.md:18`, `agents/refactor-cleaner.md:13`) becomes the template propagated
to the skills. The regression check is a ~30-line grep script, not a dependency.

## 6. Load-bearing decision → `/architect`

**How to make internal references collision-proof.** Two viable strategies:

- **(A) Namespace prefix** — reference `harness-claude:planner`, `/harness-claude:plan`.
  Idiomatic (Claude Code's designed mechanism); no renames. **Con:** string-coupled to the
  plugin name — a fork/rename must update every reference (mitigated by AC-5 keying off the
  manifest).
- **(B) Unique rename** — rename agents to `harness-planner`, `harness-architect`, … so the
  *bare* name can't collide and no prefix is needed. **Pro:** fork-safe, prefix-independent.
  **Con:** larger rename; breaks the modeled-on-ECC name symmetry; uglier `subagent_type`s.
- **(C) Hybrid** — unique rename **and** rely on namespace too (belt-and-suspenders).

Recommendation to bring to `/architect`: **(A)**, because it is the platform's intended
collision mechanism and AC-5 neutralizes the fork-rename con. Decide before P1 — it
determines the exact replacement string in every edit.

---

## 7. Risks

- **R1 — Namespace form must match how the plugin actually loads.** If the prefix is wrong,
  references break *worse* than today. Mitigation: P0 verifies the canonical addressable
  name (the agent list already shows `harness-claude:<agent>` as live) before bulk edits.
- **R2 — Local-dev vs. installed loading.** When the repo is opened directly (not via
  `/plugin`), skills may load unnamespaced. Mitigation: document that the harness is
  validated **as an installed plugin**; the smoke test runs that way.
- **R3 — Over-coupling to plugin name.** Addressed by strategy choice (§6) + AC-5.
- **R4 — Hook nudge on companion-less hosts.** `pre-search-mgrep-nudge.js` nudges toward
  mgrep even if absent — mildly annoying, not breaking. Out of scope for v0.2; note for
  the hooks pass.

---

## 8. Smoke test — colliding-host (AC-6)

Proves the namespaced refs actually defeat a collision, not just that the grep is clean.

1. On a machine that also has `everything-claude-code` enabled (or a personal
   `~/.claude/agents/planner.md`), enable harness-claude via `/plugin`.
2. Run `/harness-claude:plan` (or `/harness-claude:harness-plan`) on a small task.
3. **Pass:** the planning step delegates to `harness-claude:planner` — confirm via the
   agent's English SDLC output shape (phased plan + exit checks), not the foreign
   planner's format. **Fail:** output matches a non-harness planner.
4. Repeat for one reviewer step (`/harness-claude:review` → `harness-claude:code-reviewer`).

Automated guard (always available, no colliding host needed):
`./scripts/check-reference-integrity.sh` — green means zero bare internal references.

## 9. Definition of done

All ACs met; `/harness-claude:plan` smoke-tested on a colliding host invoking the
harness's own planner; README states bundled-vs-optional; CI guard green. Then — and only
then — Phase 2 (eval loops) builds on a harness whose wiring is trustworthy.
